# Toolchain, build, and package ownership

> Locally authored enforcement guidance, not a primary source or generated snapshot; source gap: live verification of current language, provider, and tool claims against authority sources (see `enforcement-sources.md`) is required.

Use this reference to identify the files that own architecture before adding,
moving, or generating source. A tool name alone is insufficient. Determine its
role, authority, and resolution domain from repository evidence.

## 1. Classify the tool before changing the tree

One product can fill several roles. Record the roles evidenced by the repository,
not its marketing label.

| Role | Architectural effect | Typical examples |
| --- | --- | --- |
| **Compiler toolchain** | Defines language/ABI, target triples, standard library, sysroot, linker, and sometimes formatting/testing. It does not necessarily own the dependency graph. | GCC, Clang/LLVM, MSVC, Intel oneAPI, ARM toolchains, `rustc`, Go toolchain, Swift toolchain, JDK, .NET SDK, Zig |
| **Build-model generator** | Owns targets and relationships, then emits files for an executor or IDE. Edit the model; generated executor files come from the generator. | CMake, Meson, Autotools, Premake, GN, Tuist, some framework project generators |
| **Build executor** | Schedules commands from an existing graph; it may not own target intent. | Ninja (designed to consume generated input), Make in executor-only use, MSBuild, `xcodebuild` |
| **Integrated build system** | Models and executes targets, often with hermetic dependency and toolchain support. | Bazel, Buck2, Pants, Gradle, Maven, Cargo, Go, SwiftPM, `zig build`, Xmake |
| **Dependency manager** | Resolves third-party versions/sources and records a manifest and often a lockfile. | Conan, vcpkg, Cargo, NuGet, Maven/Gradle, npm/pnpm/Yarn, Composer, Bundler, Poetry/uv, Hex, opam |
| **Workspace manager** | Coordinates multiple packages/projects and constrains local dependency relationships. | Cargo workspaces, pnpm/Yarn/npm workspaces, Gradle composite/multi-project builds, Maven reactor, Nx, Rush, Lerna, Go workspaces |
| **Task runner** | Names developer/CI workflows but should delegate compilation/package resolution to owning tools. | Make in wrapper use, Just, Task, Rake, Nox, Invoke, npm scripts |
| **Bundler / transformer** | Produces runtime assets from source graphs; it is not automatically the package manager. | esbuild, Rollup, Vite, Webpack, Rspack, Parcel, SWC |
| **Framework CLI** | Generates or invokes framework-specific code/build/deploy workflows. Generated ownership depends on the framework. | Angular CLI, Next/Expo CLI, Rails, Django management commands, Flutter, `dotnet`, Spring Boot plugins |
| **Environment / system manager** | Pins shells, compilers, OS packages, or deployment environments around language tools. | Nix, Guix, Conda/Mamba, asdf/mise, devcontainers, Docker/BuildKit |

Classify Ninja as a build executor, Conan as a dependency manager, Vite as a
bundler, and a root `Makefile` as an architectural owner only when its recipes
prove that role.

## 2. Determine authoritative and generated artifacts

### Authority classes

Classify every relevant artifact before editing it:

| Class | Policy | Examples |
| --- | --- | --- |
| **Authored model** | Commit and review. Change architecture here. | `CMakeLists.txt`, `meson.build`, `xmake.lua`, `BUILD.bazel`, `build.gradle.kts`, `Cargo.toml`, `pyproject.toml`, `Package.swift` |
| **Resolved lock** | Commit for applications, tools, and reproducible workspaces. For published libraries, omit only when the ecosystem intentionally tests broad consumer resolution and the exception is documented. Update through the owning resolver. | `Cargo.lock`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`, `composer.lock`, `Gemfile.lock`, `Package.resolved` |
| **Generated, committed contract** | Commit only when consumers or builds cannot regenerate it cheaply/reliably. Regenerate from its declared source; do not hand-edit. | API clients, protobuf bindings, checked-in Xcode project generated by Tuist, language lock snapshots required by release tooling |
| **Generated, ephemeral output** | Ignore and recreate. Review generated output as reproducible output, not authored architecture. | `build/`, `dist/`, `target/`, `.gradle/`, CMake cache/tree, Meson build dir, `.dart_tool/`, `node_modules/`, virtual environments |
| **Vendored third-party source** | Keep isolated with provenance, version, license, and update procedure. Do not refactor or reformat as first-party code. | `vendor/`, `third_party/`, Git submodule/export trees |
| **IDE/user state** | Ignore unless the platform explicitly treats a shared project/workspace file as authoritative. Keep personal state out of commits. | `.idea` caches, `xcuserdata`, `.vs`, editor histories |

### Non-negotiable generated-file rules

1. Find the generator command, input, version pin, and clean-tree reproduction path.
2. Change the source model, regenerate, and review the semantic diff.
3. Put generated output under an explicit path or target. Do not mix it
   indistinguishably with authored domain code.
4. Do not run formatters that make generated output diverge from regeneration.
5. Keep caches, downloaded dependencies, compiler output, and local
   absolute paths.
6. Commit exactly one supported lockfile per resolution domain. Multiple JS or
   Python lockfiles in one package are a defect unless an explicit compatibility
   workflow owns them.
7. Do not infer that an artifact is safe to delete because it is generated. First
   confirm whether releases or downstream consumers require it to be committed.

### Frequently confused native artifacts

| Signal | Authoritative when | Generated / forbidden to hand-edit when |
| --- | --- | --- |
| `Makefile` | The repository authors rules directly. | Emitted by CMake, Automake, qmake, or another generator. Edit `CMakeLists.txt`, `Makefile.am`, or the upstream model instead. |
| `build.ninja` / `*.ninja` | Direct authorship is technically possible but exceptional and must be evidenced by repository policy. | Normally emitted by CMake, Meson, GN, or another higher-level build system; Ninja is the executor, so edit the generating model. |
| `.sln`, `.vcxproj`, `.csproj` | Native MSBuild/.NET projects are the chosen model. | Emitted by CMake/Premake/another generator; edit generator inputs. SDK-style `.csproj` is normally authored even when `obj/` files are not. |
| `.xcodeproj`, `.xcworkspace` | The Xcode project is intentionally maintained and shared. | Emitted by Tuist/XcodeGen/CMake; edit `Project.swift`, `project.yml`, or generator model. Keep `xcuserdata` generated from personal state. |
| `configure`, `Makefile.in` | A release policy requires generated Autotools outputs for consumers without toolchain prerequisites. | During development, `configure.ac` and `Makefile.am` remain the authored model; regenerate rather than patch outputs. |
| IDE metadata | A checked-in platform project defines targets/resources. | It is per-user state, cache, index, or generated projection. |

## 3. Detect and resolve competing signals

Inspect root and changed-subtree evidence before selecting commands:

1. Read repository instructions and CI workflows.
2. Locate manifests, lockfiles, workspace declarations, tool-version pins, and
   generated-file headers.
3. Trace the production command from CI or release scripts to the owning model.
4. Inspect two representative target/package definitions and their tests.
5. Confirm whether a root command delegates to subtree-native tools or replaces
   their graphs.

When signals conflict, use this precedence:

1. release/CI path that produces the shipped artifact;
2. explicit architecture or contributor documentation;
3. pinned wrapper and workspace configuration;
4. manifest plus its matching lockfile;
5. local convenience scripts;
6. installed tools or untracked files, which are not authoritative toolchain
   configuration. Non-ignored untracked source is still candidate architecture
   and must be included in the topology map and full Git-visible audit;
   Gitignored untracked files are outside that inventory boundary.

Hard-line decisions:

- If both `CMakeLists.txt` and `build.ninja` exist and CMake generates Ninja,
  edit CMake only.
- If `pnpm-lock.yaml` and `package-lock.json` coexist without a compatibility
  workflow, stop resolution drift and select the manager evidenced by CI and
  `packageManager`.
- If Bazel wraps a Cargo/npm/Maven subtree, determine whether Bazel imports its
  lock/resolution or merely invokes it. Do not maintain two independent version
  graphs for the same dependencies.
- If a task runner duplicates compiler flags or source lists from the owning
  build model, remove the duplication or make it call the owner.
- If generated project files are committed, require a clean CI regeneration
  check or document why byte-for-byte reproduction is unavailable.

## 4. Native and systems ecosystems

### C, C++, Objective-C, Fortran, and mixed native code

| Signals | Role and ownership implications | Verification from a clean/out-of-tree build |
| --- | --- | --- |
| `CMakeLists.txt`, `cmake/`, `CMakePresets.json` | **CMake** is a build-model generator. Targets own source lists, include visibility, compile features, and link dependencies. Prefer presets over undocumented local flags. Edit its model and regenerate the Make/Ninja/IDE tree. | `cmake --preset <preset>` then `cmake --build --preset <preset>` and `ctest --preset <preset>`; otherwise `cmake -S . -B build && cmake --build build && ctest --test-dir build`. |
| `meson.build`, `meson_options.txt` | **Meson** owns target graphs and normally generates Ninja. Subprojects/wraps are explicit dependency boundaries; patch generated Ninja through the Meson model. | `meson setup build && meson compile -C build && meson test -C build`. |
| `xmake.lua`, `xmake-requires.lock` | **Xmake** integrates build modeling/execution and can resolve packages. Targets and visibility belong in `xmake.lua`; commit the lockfile when reproducibility is expected. | `xmake f -m debug && xmake && xmake run <target>`; use project-defined `xmake test`/task where present. |
| `Makefile`, included `.mk` files | **Make** may own the graph or only wrap other tools. If authored, keep recursive boundaries explicit and avoid duplicated source/flag lists. If generated, never patch it. | `make -n <target>` to inspect, then the documented `make clean all test`; avoid assuming target names. |
| `build.ninja` without generator evidence | **Ninja** is designed as an executor for input generated by a higher-level build system. Direct authorship is exceptional; search CI/scripts and file headers for the missing generator before editing. | `ninja -C <build-dir> -t targets`, then `ninja -C <build-dir>`; test through the owning generator or target. |
| `WORKSPACE`, `WORKSPACE.bazel`, `MODULE.bazel`, `BUILD`, `BUILD.bazel` | **Bazel** owns hermetic target/package visibility and often external resolution. `MODULE.bazel`/repository rules and BUILD targets are authoritative; `bazel-*` outputs are ephemeral. Enforce `visibility` and avoid monolithic wildcard targets. | `bazel test //path/to/...`; use `bazel query`/`cquery` to prove dependency and target ownership. |
| `buck2.toml`, `BUCK`, `TARGETS` | **Buck2** owns target graphs and visibility. Keep cells and package boundaries intentional; do not treat generated output links as source. | `buck2 test //path/to/...`; use `buck2 targets`/`buck2 audit` according to the pinned version. |
| `configure.ac`, `Makefile.am`, `m4/` | **Autotools** generates `configure` and make inputs. Edit macro/model sources; commit generated release artifacts only if repository policy requires them. | `autoreconf -fi && ./configure && make && make check` in a disposable/out-of-tree build where supported. |
| `premake5.lua`, `BUILD.gn`, `*.pro` | **Premake/GN/qmake** generate executor/IDE models. Their scripts own targets; generated projects/Ninja files do not. | Run the pinned generator, build its selected backend, then use the project test target. Exact commands are repository/version-specific. |
| `.sln`, `.vcxproj`, `.props`, `.targets` without generator evidence | **MSBuild/Visual Studio** owns configurations, target references, imports, and item visibility. Shared `.props/.targets` are policy code; user files and `obj/` are not. | `msbuild <solution-or-project> /m /t:Build` and the repository's test runner, or `dotnet build` for compatible SDK-style projects. |

#### Native dependency managers

| Signals | Ownership and artifact policy | Verification |
| --- | --- | --- |
| `conanfile.py` / `conanfile.txt`, `conan.lock`, profiles | **Conan** owns dependency recipes, options, binaries, and possibly toolchain generation. Keep profiles/tool requirements explicit; commit locks for reproducible applications. `CMakeToolchain`, `CMakeDeps`, and equivalent integration output are generated and forbidden to hand-edit. | Run the pinned Conan major version's install with repository profile/lock and missing-binary policy, then invoke the generated CMake preset/toolchain through the owning build. Conan 1/2 syntax differs. |
| `vcpkg.json`, `vcpkg-configuration.json`, `vcpkg-lock.json`, overlays | **vcpkg** manifest mode owns ports/features/baseline. Commit manifest/configuration and applicable lock/baseline data; keep overlays owned and reviewed. Edit the manifest and configuration; keep installed trees generated. | `vcpkg install` or configure through the repository's CMake/MSBuild integration; use the pinned vcpkg executable/baseline. |
| `.pc` files / `pkg-config` calls | **pkg-config** supplies discovery metadata; it does not resolve or build dependencies. Authored templates may be source; installed/generated `.pc` files are outputs. | `pkg-config --cflags --libs <name>` plus the owning build. |
| Git submodules, `third_party/`, CPM/FetchContent | This is vendoring/source acquisition, not automatic architectural ownership. Pin immutable revisions, isolate patches, licenses, and update procedure; prevent private dependency APIs leaking into public headers. | Recreate from a clean checkout with submodules/dependency downloads and run the owning native build. |

Use Conan and vcpkg together for one dependency domain only with a written
split. Keep compiler flags in the model that owns targets rather than copying
them among CMake, Make, and CI scripts. Expose supported configuration inputs.

### Other compiled/system ecosystems

| Ecosystem and signals | Owner model | Focused verification |
| --- | --- | --- |
| **Rust:** `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` | Cargo owns crates, features, profiles, dependencies, and workspaces. Commit `Cargo.lock` for binaries/workspaces; published-library policy may differ intentionally. `target/` is ephemeral. | `cargo fmt --check`; `cargo check --workspace --all-targets`; `cargo test --workspace` with project feature policy. |
| **Go:** `go.mod`, `go.sum`, optional `go.work`/`go.work.sum` | Go modules own dependency versions; packages own compilation. Commit module sums. Use `go.work` only for an intentional local/monorepo workspace, not published module coupling. | `go test ./...`; `go vet ./...`; in multi-module repos run per module or the documented workspace command. |
| **Zig:** `build.zig`, `build.zig.zon` | Zig's build runner owns modules/artifacts; the zon manifest owns declared dependencies. Cache directories are ephemeral. API details vary by Zig version, so obey the pinned compiler. | `zig build`; `zig build test` when the build exposes that step. |
| **D:** `dub.json`/`dub.sdl`, `dub.selections.json` | Dub owns packages/configurations and resolution. Commit selections when the repository uses reproducible application resolution. | `dub build`; `dub test`. |
| **Ada:** `alire.toml`, `alire.lock`, `.gpr` | Alire owns package resolution/toolchain environment; GPRbuild project files own units/libraries/build modes. Generated configuration is not authored source. | `alr build`; `alr test` when defined, or `gprbuild -P <project>`. |
| **Fortran:** `fpm.toml` | fpm integrates package/build/test ownership. With CMake/Meson, those native models own targets instead. | `fpm build`; `fpm test`. |
| **Odin:** collection/import conventions plus `build.odin`, Make/Task scripts, or CI | No single universal project manager is assumed. Treat the evidenced build entrypoint as owner and keep foreign libraries explicit. | `odin check <package>` and repository test/build commands. |
| **C3:** `project.json`/tool-version-specific project files or scripts | Tooling conventions are still version-sensitive. Use only fields/commands evidenced by the installed/pinned C3 toolchain and repository. | Run the documented `c3c` project build/test command; do not invent flags from memory. |

## 5. Managed VM and mobile ecosystems

| Signals | Role and ownership implications | Focused verification |
| --- | --- | --- |
| `pom.xml`, `.mvn/`, `mvnw` | **Maven** owns reactor modules, lifecycle, dependencies, plugins, and source sets. Parent POMs define policy; BOMs constrain versions. Prefer the wrapper. `target/` is ephemeral. | `./mvnw test` or a focused `./mvnw -pl <module> -am test`; use `verify` when integration plugins bind there. |
| `settings.gradle(.kts)`, `build.gradle(.kts)`, `gradlew`, version catalogs | **Gradle** owns multi-project/source-set/task graphs and dependency resolution. Commit wrapper and lock/verification metadata used by policy; never edit `.gradle/` or generated build output. | `./gradlew test`; use `:<project>:check` for a focused module and project-defined quality tasks. |
| `build.sbt`, `project/`, `plugins.sbt` | **sbt** owns Scala/JVM modules, configurations, and dependencies. Keep settings scoped; `target/` and generated BSP metadata are outputs. | `sbt test` or `sbt <project>/test`. |
| `build.sc` / `build.mill` | **Mill** integrates JVM/Scala build targets. The build definition owns module topology; `out/` is generated. Syntax is version-sensitive. | `./mill __.test` or the repository's focused module target. |
| `deps.edn`, `build.clj`, `project.clj` | Clojure CLI/tools.build or **Leiningen** owns classpaths, aliases/tasks, and dependencies. Select one primary path from CI evidence. | `clojure -X:test`/documented alias or `lein test`. |
| `.sln`, SDK-style `.csproj`/`.fsproj`, `Directory.Build.*`, `global.json`, `packages.lock.json` | **dotnet CLI/MSBuild** owns projects, target frameworks, references, and build policy; **NuGet** owns package resolution. Commit SDK pin and lockfiles when locked restore is used. `bin/`/`obj/` are ephemeral. | `dotnet restore --locked-mode` when configured; `dotnet build --no-restore`; `dotnet test --no-build`. |
| `paket.dependencies`, `paket.lock` | **Paket** replaces/augments NuGet resolution. The lock is authoritative; generated references are not hand-edited. | `dotnet paket restore` or pinned Paket command, then `dotnet test`. |
| `mix.exs`, `mix.lock` | **Mix** owns Elixir apps/umbrella children/tasks; **Hex** resolves packages. Commit `mix.lock` for applications/workspaces. Keep umbrella app dependencies directed, not implicit through sibling paths. | `mix format --check-formatted`; `mix compile --warnings-as-errors`; `mix test`. |
| `rebar.config`, `rebar.lock` | **rebar3** owns Erlang/OTP applications, profiles, releases, and dependencies. Commit the lock for applications. | `rebar3 compile`; `rebar3 eunit`; `rebar3 ct` as applicable. |
| `Package.swift`, `Package.resolved` | **SwiftPM** owns packages, products, targets, and resolution. Commit resolution for applications; library policy may intentionally avoid pinning consumer dependencies. `.build/` is ephemeral. | `swift build`; `swift test`. |
| `.xcodeproj`/`.xcworkspace`, `Podfile`/`Podfile.lock`, `Cartfile.resolved`, `Project.swift`, `project.yml` | Xcode may own targets directly; **CocoaPods/Carthage** own Apple dependency integration; **Tuist/XcodeGen** generate projects. Identify the owner before editing. Commit app resolution artifacts and shared project model; keep user data/DerivedData outside commits. | Generate if applicable, then `xcodebuild -scheme <scheme> -destination <destination> test`; exact scheme/destination is project-owned. |
| Android `settings.gradle`, module builds, `gradlew` | Gradle and Android plugins own modules, variants, resources, generated source, and dependency resolution. Keep domain modules platform-free where designed; edit the source or generator that produces `build/generated`. | `./gradlew test lint`; add the relevant device/instrumented test task where the change crosses Android runtime behavior. |
| `pubspec.yaml`, `pubspec.lock`, `.metadata` | **Dart pub/Flutter CLI** own packages, plugins, and generated platform scaffolding. Commit app locks; package lock policy follows Dart publishing convention. `.dart_tool/` and `build/` are ephemeral. | `dart format --output=none --set-exit-if-changed .`; `dart analyze`; `dart test`, or `flutter analyze && flutter test`. |

## 6. JavaScript, TypeScript, and web ecosystems

### Package and workspace managers

| Signals | Ownership and hard line | Focused verification |
| --- | --- | --- |
| `package-lock.json`, `npm-shrinkwrap.json`, `workspaces` | **npm** owns resolution/workspaces. Commit one lock at workspace root. `npm-shrinkwrap.json` is a publishable lock and should be intentional. | `npm ci`; `npm test`; `npm run build`/`lint` if defined. |
| `pnpm-lock.yaml`, `pnpm-workspace.yaml` | **pnpm** owns one workspace resolution domain and strict linking. Catalogs/overrides/patches are workspace policy; commit them and the lock. | `pnpm install --frozen-lockfile`; `pnpm -r test`; use filters for focused packages. |
| `yarn.lock`, `.yarnrc.yml`, `.yarn/`, `packageManager` | **Yarn** owns workspaces/resolution; Plug'n'Play and zero-install artifacts require repository-specific commit policy. Keep PnP resolution assumptions aligned with the Yarn configuration. | `yarn install --immutable`; `yarn workspaces foreach` or project scripts. Commands differ materially between Yarn Classic and Berry; obey the pin. |
| `bun.lock`/version-specific Bun lock, `bunfig.toml` | **Bun** can own resolution, runtime, scripts, tests, and bundling. Keep its lock authoritative only when CI uses Bun. | `bun install --frozen-lockfile`; `bun test`; `bun run build` if defined. |
| `deno.json`/`deno.jsonc`, `deno.lock`, import map | **Deno** owns runtime tasks, permissions, imports, formatting, linting, and tests. Commit the lock when reproducibility is intended. Do not impose Node package layout unless compatibility is explicit. | `deno fmt --check`; `deno lint`; `deno check <entry>`; `deno test` with repository permissions. |
| `rush.json`, `nx.json`, `turbo.json`, `lerna.json`, Lage config | **Rush/Nx/Turborepo/Lerna/Lage** coordinate workspaces, caching, release, or task graphs; the underlying package manager still owns dependency resolution. Keep dependency resolution in the underlying package-manager graph. | Use the pinned orchestrator's affected/focused check, then the underlying package manager's immutable install. |
| `corepack`/`packageManager` field, Volta config | These pin or dispatch runtimes/package managers; they do not own package architecture. Respect the pin before interpreting lockfiles. | `corepack enable` only when repository setup calls for it; inspect `node --version` and manager version in reproducible environments. |

### Build, bundling, and framework layers

| Signals | Ownership and hard line | Verification |
| --- | --- | --- |
| `vite.config.*`, Rollup/esbuild/Webpack/Rspack/Parcel config | The bundler owns asset/module transformation and output chunks, while third-party resolution remains with the package manager. Keep server/browser entrypoints and environment exposure explicit; commit `dist/` only when distribution policy requires it. | Run the package's build and focused test; use production mode because development servers may hide bundling failures. |
| `tsconfig.json`, references, `tsconfig.*.json` | TypeScript configuration owns compile units, emit, path mapping, and project references. It is not a package boundary unless package exports/build targets agree. Avoid aliases that permit private cross-package imports. | `tsc -p <config> --noEmit` or repository build mode `tsc -b`. |
| Next.js, Angular, Nuxt, SvelteKit, Remix, Astro, Expo config | Framework CLIs own routing, server/client boundaries, generated types, and build conventions. Preserve required filesystem routes. Move domain logic out of framework entrypoints without fighting loader conventions. | Run framework production build plus its selected test/e2e runner. Select commands from the manifest scripts rather than applying one universal command. |
| Jest, Vitest, Mocha, Playwright, Cypress config | Test runners own discovery and environments, not product architecture. Keep unit, integration, component, and e2e projects separated when environments differ. | Run the narrow project/file, then the configured aggregate test script. |

Replace a package manager only for a named outcome. A migration must
update the manager pin, lockfile, CI, release/publish path, container builds,
developer bootstrap, and cache keys atomically, then remove the old lock and
calls.

## 7. Scripting, data, and functional ecosystems

| Ecosystem and signals | Owner model and artifact policy | Focused verification |
| --- | --- | --- |
| **Python:** `pyproject.toml`, `uv.lock` | **uv** can own environments, resolution, scripts, and builds around PEP standards. Commit `uv.lock` for applications/workspaces; keep `[build-system]` authoritative for package building. | `uv sync --frozen`; `uv run pytest`; invoke configured lint/type checks. |
| **Python:** `pyproject.toml`, `poetry.lock` | **Poetry** owns dependency groups, build metadata, and resolution. Commit the lock for apps. Do not also maintain `requirements.txt` unless generated for a named deployment consumer. | `poetry install`; `poetry run pytest`; `poetry build` for package proof. |
| **Python:** `pdm.lock`, `pdm.toml` or Hatch config | **PDM/Hatch** own environment/workflow/build concerns according to config. Lock and generated environments follow that owner; do not mix their env managers casually. | `pdm sync --frozen-lockfile && pdm test` or `hatch run test`, per repository scripts. |
| **Python:** `requirements*.txt`, `setup.py`, `setup.cfg`, pip-tools files | **pip** installs; setuptools/build backends build; pip-tools may generate pinned requirements from `.in` sources. Identify which file is source versus compiled lock. Never hand-edit generated requirements. | Create a clean venv, install with hashes/constraints where configured, run tests, and `python -m build` for distributions. |
| **Python/data:** `environment.yml`, `conda-lock.yml`, Pixi config | **Conda/Mamba/Pixi** own binary/system plus language environment resolution. Keep one environment source and lock strategy; record any pip overlay in the environment and lock strategy. | Create/sync the locked environment, then run package tests inside it. Exact commands depend on the selected manager. |
| **Python task/test envs:** `tox.ini`, `noxfile.py`, Invoke config | Tox/Nox coordinate environment matrices; Invoke is a task runner. They must consume, not independently redefine, package dependencies except explicit test extras. | `tox`/`nox` selected sessions after a focused native environment test. |
| **Ruby:** `Gemfile`, `Gemfile.lock`, gemspec, `Rakefile` | Bundler owns app resolution, RubyGems/gemspec owns published dependency ranges, Rake owns tasks. Keep gemspec and Gemfile roles distinct; commit app locks. | `bundle install`; `bundle exec rake test` or repository RSpec command; `gem build` for packages. |
| **PHP:** `composer.json`, `composer.lock` | Composer owns PSR autoload maps, dependency resolution, scripts, and plugins. Commit locks for applications; library policy may test ranges. `vendor/` is normally ephemeral. | `composer install --no-interaction`; `composer validate`; run configured test/static-analysis scripts. |
| **Haskell:** `.cabal`, `cabal.project`, `cabal.project.freeze`, `stack.yaml`, `stack.yaml.lock` | Cabal owns packages/components; Stack owns curated resolver/workspace orchestration. Select the CI path as primary. Freeze/lock files are app/workspace policy, not universal library requirements. | `cabal build all && cabal test all` or `stack test`. |
| **OCaml:** `dune-project`, `dune`, `opam` files, `opam.locked` | Dune owns build component/module visibility; opam owns packages/environments. Generated opam files must follow the declared Dune generation policy. | `dune build @all`; `dune runtest`; use the pinned opam switch/environment. |
| **R:** `DESCRIPTION`, `NAMESPACE`, `renv.lock` | R package metadata owns distribution; renv/pak own environment resolution. Generated roxygen documentation/NAMESPACE must be regenerated, not patched. | `R CMD check`; restore the locked environment first when used. |
| **Julia:** `Project.toml`, `Manifest.toml` | Pkg owns project dependencies; Manifest pins the full environment and should be committed for applications/research reproducibility. Package-library manifest policy may intentionally differ. | `julia --project -e 'using Pkg; Pkg.instantiate(); Pkg.test()'`. |
| **MATLAB:** `.prj`, toolbox/project files, `matlab.unittest` suites | MATLAB projects/toolboxes own paths, dependencies, shortcuts, and packaging. Generated code/cache directories are not authored source. | Run the repository's `matlab -batch` test/build entrypoint; releases/toolboxes may require licensed products. |
| **Perl:** `cpanfile`, `META.*`, `Makefile.PL`/`Build.PL`, `Carton` snapshot | CPAN metadata/build tools own distribution; Carton/local-lib may pin app dependencies. Generated Makefiles are outputs. | Install in an isolated environment, then `prove -lr t` and distribution build/check. |

## 8. Polyglot monorepos and orchestration

### Root orchestrators

| Signals | Valid role | Architectural constraint |
| --- | --- | --- |
| Bazel/Buck2/Pants root | Hermetic cross-language target graph, cache, and dependency policy. | Declare small owned targets, visibility, code generation, and toolchains explicitly. Do not add a second invisible dependency graph in shell scripts. |
| Nix/Guix, devcontainer, mise/asdf | Reproducible developer/compiler/system environment. | Pin runtimes and system inputs, then delegate package resolution to language owners unless one system intentionally owns the complete closure. |
| Earthly, Dockerfile/BuildKit, Compose | Image/build/development environment orchestration. | Multi-stage images consume verified outputs or invoke canonical builds. Keep Docker source/dependency lists aligned with native manifests. |
| Make/Just/Task at root | Stable human/CI entrypoint delegating to subtree owners. | Recipes must call native tools, propagate failures, avoid duplicating versions/flags, and expose focused targets. |
| CI workflow YAML | Automation policy and job graph. | CI invokes canonical commands; manifests and tool owners define source lists, compiler flags, and dependency versions. |

### Monorepo rules

1. Define resolution domains explicitly: one workspace lock where tools support
   it, or intentionally isolated locks aligned with deploy/release ownership.
2. Give each package one canonical build/test command and one owner. Root
commands compose those commands; they preserve their ownership.
3. Represent cross-package dependencies in manifests/target graphs, with CI
ordering and filesystem-relative imports serving as supporting evidence.
4. Enforce visibility using the strongest available mechanism: Bazel/Buck
   visibility, package exports, `internal/`, module descriptors, project
   references, access modifiers, or dependency lint rules.
5. Centralize versions only when the ecosystem supports a single resolution
   policy. Keep versions in native manifests or generate a shared file from
   them.
6. Put code generation in the graph with declared inputs/outputs and pinned
   generator versions. Run generation once at its contract owner, not separately
   with consumer-specific flags.
7. Cache only reproducible outputs keyed by source, lockfiles, toolchain,
   target, and relevant environment. A cache hit is not validation.
8. Make affected-only execution an optimization over a correct full graph. Pair
   path filters with a dependency graph when they determine execution scope.
9. Keep deployables independent of repository-root runtime state. A monorepo is
   a collaboration boundary, not a license for implicit production coupling.
10. Reject root-level `vendor`, `generated`, or `shared` ownership without a
   named subsystem, provenance, consumers, and update/release policy.

### Cross-language contract ownership

For Protobuf, OpenAPI, GraphQL, Thrift, FlatBuffers, database schemas, or FFI:

- declare the schema/IDL owner and compatibility policy;
- pin the generator and plugins;
- isolate generated outputs per language/package;
- regenerate outputs through the owning generator;
- verify regeneration leaves a clean tree;
- test producer and consumer compatibility, not compilation alone;
- version breaking contracts and coordinate release order;
- keep FFI allocation, error, threading, and ABI ownership documented at the
  boundary.

## 9. Verification protocol

Select the narrowest command chain that
proves the changed owner, then run the repository-required aggregate checks.

### Before editing

```sh
# Examples; adapt to repository tooling and avoid generated/vendor trees.
find . -maxdepth 3 -type f \
  \( -name 'CMakeLists.txt' -o -name 'meson.build' -o -name 'xmake.lua' \
     -o -name 'BUILD.bazel' -o -name 'Cargo.toml' -o -name 'go.mod' \
     -o -name 'pom.xml' -o -name 'build.gradle*' -o -name 'package.json' \
     -o -name 'pyproject.toml' -o -name 'Package.swift' \) -print
```

Then inspect CI/release calls, wrapper versions, workspace roots, lockfiles,
source/include/test declarations, generated headers, and target visibility.

### After structural changes

1. Run the canonical formatter/linter only on authored source.
2. Configure/resolve from a clean or out-of-tree state with locked/frozen mode.
3. Build/type-check the smallest affected target and all direct dependents.
4. Run owner-local unit tests.
5. Run integration/contract tests crossing any moved public boundary.
6. Regenerate committed outputs and require a clean regeneration diff.
7. Query the build graph or inspect dependency output to prove direction and
   visibility where the tool supports it.
8. Run repository-required aggregate checks.
9. Confirm ignored outputs, caches, local paths, and alternate lockfiles were
   not introduced.

### Architecture acceptance gate

Reject the change when any of these remain unexplained:

- two tools independently own the same dependency versions or source list;
- a task runner has become an undeclared build system;
- generated output was edited without its source/generator changing;
- a lockfile changed without a manifest, resolver, or platform reason;
- a new package can import another package's private source path;
- root orchestration is required for a subtree's basic local test without a real
  cross-subtree dependency;
- a build passes only from a dirty or pre-populated workspace;
- target visibility, public headers/exports, or source sets grew broader than
  the requested capability requires;
- CI, developer, release, and container builds invoke different authoritative
  graphs without an explicit compatibility purpose.

Tool syntax and lockfile behavior can change across major versions. When a
repository pins a version, its local help, wrapper, schema, and generated
headers override generic command examples here.
